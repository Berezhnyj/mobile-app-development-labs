# :bookmark_tabs: Лабораторна робота №6
## Тема: "Архітектурний рефакторинг та управління станом застосунку (State Management)"

### 1. Мета роботи
Перехід від примітивного локального управління станом (`setState`) до промислових архітектурних патернів. Розділення шару представлення (UI) та бізнес-логіки, опанування механізмів односпрямованого потоку даних (Unidirectional Data Flow) та впровадження інверсії залежностей (Dependency Injection).

---

### 2. Завдання до лабораторної роботи

**Мета завдання:** Здійснити тотальний рефакторинг кодової бази, замінивши пряме управління станом у віджетах на обрану систему State Management (BLoC, Cubit, Redux, Riverpod тощо). 

**Функціональні вимоги та Архітектурні Обмеження (Acceptance Criteria):**

1. **Тотальна ліквідація `StatefulWidget`:**
   - 95% вашого UI має бути побудовано на `StatelessWidget`.
   - **Виняток:** Допускається використання `StatefulWidget` **виключно** для управління локальним станом UI (Local UI State), а саме: робота з `TextEditingController`, `AnimationController`, `ScrollController`. Використання `setState` для зміни бізнес-даних (списків, профілю) — **категорично заборонено**.
2. **Абсолютна ізоляція шару даних (UI is Dumb):**
   - Віджети не повинні знати про існування бази даних чи мережі. Прямий виклик методів API або репозиторіїв із коду віджета (наприклад, з `onPressed`) призведе до миттєвого незарахування роботи.
   - Комунікація з API відбувається **тільки** через класи State Management (наприклад, UI відправляє `Event` у BLoC -> BLoC викликає Repository -> BLoC емітить новий `State` -> UI перемальовується).
   - *Виняток:* Логіку базового автологіну (перевірка токена при старті) можна залишити на рівні точки входу.
3. **Singleton та Dependency Injection:**
   - Класи API, репозиторії та сервіси повинні створюватися **лише один раз** за весь життєвий цикл застосунку (Singleton).
   - Виклик конструктора `MyRepository()` всередині віджетів чи блоків є порушенням архітектури. Об'єкти мають передаватися через DI-контейнер (наприклад, `get_it`) або через конструктор. Повторне створення інстансу вимагатиме жорсткої аргументації на захисті.
4. **Реактивний рендеринг CRUD-операцій:**
   - Відображення списків (FutureBuilder замінюється на State-віджети, наприклад, `BlocBuilder`), створення, редагування та видалення даних повинні базуватися виключно на реакції UI на зміну глобального стану.
5. **Жорсткий ліміт файлів (Clean Code):**
   - Розмір жодного файлу **не повинен перевищувати 150 рядків коду (LOC)**. Це змусить вас декомпозувати логіку на States, Events, Blocs/Cubits та UI-компоненти.

---

### 3. Порядок виконання

#### 3.1. Синхронізація репозиторію
1. Успішний захист Лабораторної роботи №5 є блокером.
2. Змерджити гілку `feature/lab-5-network` у `main`.
3. Створити нову гілку `feature/lab-6-state-management` від актуального `main`.

#### 3.2. Рефакторинг бізнес-логіки
1. Вибрати інструмент State Management (рекомендується **BLoC** або **Cubit** як індустріальні стандарти, або **Redux** для функціонального підходу).
2. Створити директорії для управління станом (наприклад, `logic/` або `blocs/`).
3. Визначити стани (States), які може приймати ваш екран (наприклад: `Initial`, `Loading`, `Loaded(List<Data>)`, `Error(String message)`). Усі стани мають бути імутабельними (Immutable).
4. Перенести всю логіку виклику API із віджетів у класи стейт-менеджменту.

#### 3.3. Впровадження Dependency Injection
1. Видалити всі прямі інстанціації репозиторіїв.
2. Створити єдиний файл ініціалізації залежностей або використати `RepositoryProvider` на вершині графа віджетів.

### 4. Вимоги до звітності

1. **Pull Request:**
   - Створити PR із гілки `feature/lab-6-state-management` у `main`.
   - В описі PR чітко розписати: який State Management обрано, як реалізовано Dependency Injection, та навести приклад потоку даних (Data Flow) від натискання кнопки до оновлення екрану.
2. **Код-рев'ю:**

3. **Документація:** Оновити документ з лабораторними.

### 5. Критерії оцінювання

| Критерій | Вага |
|----------|------|
| Викорінення `StatefulWidget` (крім винятків) та перехід на State Management | 25% |
| Ізоляція бізнес-логіки: відсутність викликів API у шарі UI | 25% |
| Імплементація DI/Singleton для сервісів та репозиторіїв | 20% |
| Реактивна обробка CRUD-операцій через глобальний стан | 15% |
| Дотримання інженерних обмежень (< 150 LOC) та форматування коду | 15% |

### 6. Вимоги до захисту (Контрольні питання)

Цей захист є стрес-тестом вашого розуміння архітектури застосунку. Ви повинні бути готові до:
1. **Live Coding:** На вимогу викладача за 5-10 хвилин з нуля створити нову просту логіку з використанням обраного стейт-менеджменту (наприклад, лічильник або тоггл теми), коректно розділивши UI та бізнес-логіку.
2. **Компіляція:** Чітко пояснити різницю між **AOT** (Ahead-of-Time) та **JIT** (Just-in-Time) компіляцією в контексті Dart/Flutter. Яка з них використовується під час розробки (Debug), а яка — у продакшені (Release)?
3. **Архітектура:** Пояснити концепцію Unidirectional Data Flow. Чому двостороннє зв'язування даних (Two-way data binding) вважається антипатерном у сучасних фреймворках?
4. **Immutability:** Чому стани (States) у BLoC/Redux мають бути немутабельними (із ключовим словом `final` та `const`)?
