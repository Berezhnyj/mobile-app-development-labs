# :bookmark_tabs: Лабораторна робота №5
## Тема: "Інтеграція мобільного застосунку із зовнішніми програмними інтерфейсами (REST API)"

### 1. Мета роботи
Забезпечення мережевої взаємодії мобільного застосунку із зовнішніми серверами, опанування HTTP-клієнтів, реалізація асинхронного рендерингу UI та впровадження механізмів локального кешування (Offline-First підхід) для забезпечення відмовостійкості системи при втраті зв'язку.

---

### 2. Завдання до лабораторної роботи

**Мета завдання:** Підключити застосунок до віддаленого джерела даних (REST API або Firebase), реалізувати отримання, парсинг (JSON) та відображення даних, зберігши при цьому попередньо напрацьовану архітектуру абстракцій.

**Функціональні вимоги:**
1. **Мережева взаємодія:** Імплементувати отримання даних з віддаленого сервера. Дозволяється використовувати власний бекенд, Firebase (Cloud Firestore/Realtime DB) або публічні mock-сервіси (наприклад, MockAPI, JSONPlaceholder).
2. **Асинхронний UI:** Застосувати віджет `FutureBuilder` (або `StreamBuilder` для Firebase) для обробки та відображення станів мережевого запиту: `Loading` (індикатор), `Success` (дані), `Error` (повідомлення про помилку).
3. **Офлайн-кешування (Offline-First Strategy):** 
   - Інформація про профайл користувача (нікнейм, email тощо) має кешуватися локально.
   - Основний масив даних (списки IoT-пристроїв, розклад, таски тощо) повинен зберігатися в локальній БД при успішному мережевому запиті.
   - У разі відсутності інтернету застосунок **не повинен** показувати помилку підключення одразу. Він має завантажити та відобразити останні закешовані дані (модифікація кешованих даних в офлайні не вимагається).
4. **Авторизація:** Логіка автологіну залишається (через перевірку локального кешу). Реалізація повноцінної Token-based авторизації (збереження та передача JWT-токена в заголовках HTTP-запитів) вважатиметься значною інженерною перевагою.

**Критерії приймання (Acceptance Criteria) та архітектурні обмеження:**
- **Поліморфізм та Інверсія залежностей:** Мережева імплементація повинна наслідувати ті ж абстрактні інтерфейси (наприклад, `IRepository`), які ви створили в Лаб. №3 для локальної БД. Заміна локального джерела на мережеве має відбуватися на рівні ініціалізації (Dependency Injection), без переписування коду UI.
- **Жорсткий ліміт файлів (Clean Code):** Розмір жодного файлу (особливо з UI) **не повинен перевищувати 150 рядків коду (LOC)**. Це змусить вас винести DTO (Data Transfer Objects), мапери, мережеві клієнти та віджети у незалежні структури.
- **Обробка виключень (Exception Handling):** Мережеві запити нестабільні за своєю природою. Кожен виклик API має бути загорнутий у блок `try-catch`. Будь-який HTTP-статус, відмінний від 2xx, повинен коректно перехоплюватись і транслюватись у зрозуміле користувачу повідомлення, а не "вбивати" додаток.

### 3. Порядок виконання

#### 3.1. Синхронізація репозиторію
1. Успішний захист Лабораторної роботи №4 є блокером.
2. Змерджити гілку з Лаб. №4 у `main`.
3. Створити нову гілку `feature/lab-5-network` від актуального стану `main`.

#### 3.2. Імплементація мережевого шару
1. Обрати HTTP-клієнт (`http` або `dio`) чи ініціалізувати Firebase SDK.
2. Створити моделі даних (Models) та реалізувати методи `fromJson` / `toJson` для серіалізації/десеріалізації JSON.
3. Написати нову імплементацію репозиторію (наприклад, `RemoteApiRepository`), яка робить HTTP-запити.

#### 3.3. Реалізація кешування та UI
1. Налаштувати логіку репозиторію: спочатку спробувати отримати дані з мережі -> при успіху зберегти їх у локальну БД -> повернути на UI. При помилці мережі -> дістати дані з локальної БД -> повернути на UI.
2. Інтегрувати `FutureBuilder` у ваші екрани для реакції на процес завантаження.

### 4. Вимоги до звітності

1. **Pull Request:**
   - Створити PR із гілки `feature/lab-5-network` у `main`.
   - В описі PR пояснити обраний стек (REST API vs Firebase, `http` vs `dio`) та описати механізм кешування.
2. **Стрес-тест (Відеодемонстрація):**
   - Показати успішне завантаження даних з сервера при наявності Інтернету.
   - **Критичний тест:** Примусово вимкнути Wi-Fi/Mobile Data на девайсі/емуляторі, перезапустити застосунок (або оновити сторінку) і продемонструвати, що застосунок не впав, а успішно завантажив та відобразив збережені офлайн-дані.
3. **Документація:** Оновити документ з лабораторними.

### 5. Критерії оцінювання

| Критерій | Вага |
|----------|------|
| Мережева взаємодія: коректний парсинг JSON, робота з API/Firebase | 25% |
| Інтеграція UI: використання `FutureBuilder` (Loading, Success, Error states) | 20% |
| Offline-First: кешування та успішне відновлення даних без Інтернету | 25% |
| Архітектура: дотримання ліміту <150 LOC, перевикористання інтерфейсів | 15% |
| Надійність: обробка HTTP-помилок та виключень | 15% |

### 6. Вимоги до захисту (Контрольні питання)

Студент повинен продемонструвати інженерну зрілість у таких питаннях:
1. **HTTP Протокол:** Які існують HTTP-методи (GET, POST, PUT, PATCH, DELETE) і коли їх доцільно використовувати? Що означають статуси 200, 400, 401, 404, 500?
2. **Мережеві клієнти:** Поясніть різницю між пакетами `http` та `dio`. Які переваги дає `dio` (наприклад, Interceptors, Cancel Tokens)?
3. **Парсинг:** Як працює серіалізація JSON у Dart? Чому небезпечно парсити великі JSON-файли в основному потоці і що таке `Isolates`?
4. **BaaS (Backend as a Service):** Що таке Firebase? Які ключові сервіси він пропонує для мобільних застосунків (Authentication, Firestore, Cloud Functions)?
5. **State Management (FutureBuilder):** Чим відрізняється `FutureBuilder` від виклику `setState` всередині `.then()`?
